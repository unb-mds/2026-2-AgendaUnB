    Plano de hospedagem e CI/CD

    Operação da S7-B06

    Em 14/11/2026, por decisão do PO de manter ambiente único nesta fase (sem serviços ou projetos duplicados entre homologação e produção por prazo e orçamento), agendaunb.com.br e 2026-2-agendaunb-agenda-un-b.vercel.app servem o frontend Vite na Vercel (o endereço legado agendaunb.vercel.app retorna DEPLOYMENT_NOT_FOUND). O domínio www redireciona para o domínio principal. O bundle aponta para a API no Render (agenda-unb-api-homolog) e para o projeto Supabase pzniltzdhyuzzdqbppjw (agenda-unb-homolog), com as 31 migrações versionadas aplicadas, sincronização do catálogo 2026.2 executada e supressão de uvicorn.access quando APP_ENV != "local".

    Componente Configuração ativa
    SPA Vercel, raiz frontend (e configuração equivalente na raiz em vercel.json), Vite, npm ci, npm run build, saída dist. As rotas /api/search, /sitemap.xml, /evento/:id e /auth/retorno têm rewrites dedicados e ficam preservadas no fallback.
    API FastAPI em Python 3.11 no Render (agenda-unb-api-homolog). Usar HTTPS direto para /api/v1, inclusive no upload. O Blueprint em render.yaml reflete o serviço único Free com publicação manual.
    Auth, dados e Storage Projeto Supabase único pzniltzdhyuzzdqbppjw (agenda-unb-homolog), compartilhado entre API, frontend e jobs, com 31 migrações aplicadas até 20261113212429 e conexão PostgreSQL via TLS (sslmode=require).
    Worker, coletor e catálogo GitHub Actions com segredos no environment production-jobs e disparo manual/agendado por job (worker, collector e catalog para python -m src.modules.classes.sync --period 2026.2), validando a operação de custo zero da #68.

    O PDF vai diretamente do navegador para o Render com Bearer do Supabase e multipart. O limite é 10 MiB (10.485.760 bytes), com espaço adicional para o envelope multipart. A API prepara o texto privado e descarta o PDF original. A revisão e a autorização do texto continuam necessárias para iniciar processamento por IA. A Vercel limita o payload de Functions a 4,5 MB. Limites da Vercel.

    Local Variáveis e configuração
    Vercel VITE_API_URL com https://agenda-unb-api-homolog.onrender.com/api/v1, VITE_SUPABASE_URL e VITE_SUPABASE_PUBLISHABLE_KEY do projeto pzniltzdhyuzzdqbppjw (chave legada anon também aceita).
    Previews Vercel Como o projeto opera com ambiente único por decisão do PO, habilitar VERCEL_ENV apenas quando houver projeto/origem de produção distintos; caso contrário, deploymentConfig.js valida que VITE_API_URL seja HTTPS terminado em /api/v1 e bloqueia variáveis VITE_* não listadas.
    Render APP_ENV=production (com uvicorn.access desativado fora de local), DATABASE_URL com TLS, SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, GOOGLE_CALENDAR_REDIRECT_URI=https://agenda-unb-api-homolog.onrender.com/api/v1/me/google-calendar/callback, GOOGLE_CALENDAR_FRONTEND_REDIRECT_URI=https://agendaunb.com.br/eventos?aba=meus e CORS_ORIGINS=https://agendaunb.com.br,https://2026-2-agendaunb-agenda-un-b.vercel.app.

    A proposta utiliza serviços gerenciados para reduzir manutenção operacional. O runtime Python dispensa o Dockerfile vazio; não executar servidor Vite de desenvolvimento nem Uvicorn com --reload em hospedagem. Não houve contratação, criação de contas ou deploy nesta entrega.

    Ambientes e configuração

    Login na Vercel e Supabase Auth

    O frontend usa VITE_SUPABASE_URL e VITE_SUPABASE_PUBLISHABLE_KEY (sb_publishable_...). VITE_SUPABASE_ANON_KEY continua aceito como alternativa legada, somente com JWT de papel anon. O build rejeita chaves sb_secret_... ou JWT service_role em qualquer variável VITE_, inclusive uma variável legada que não seja mais utilizada. Nunca incluir credenciais privadas nesse prefixo.

    Se aparecer Forbidden use of secret API key in browser, substituir a chave na Vercel nos ambientes afetados e gerar um novo deploy: Vite incorpora os valores durante o build. Revogar/rotacionar a chave secreta que foi publicada, atualizando primeiro os serviços privados que dependem dela. A chave pública fica em Supabase > Settings > API Keys.

    No Supabase hospedado, configurar Auth > URL Configuration com a URL real do site e permitir o retorno exato https://<dominio>/?auth=login. Configurar separadamente os domínios de homologação e produção. supabase/config.toml configura o ambiente local; alterá-lo não habilita provedores no projeto remoto.

    Em Auth > Sign In / Providers, manter Email habilitado e habilitar Google com o Client ID e Client Secret do cliente OAuth Web do Google Cloud. No Google, cadastrar a origem HTTPS do site e o callback fornecido pelo Supabase: https://<project-ref>.supabase.co/auth/v1/callback. Se o aplicativo Google estiver em teste, cadastrar os usuários de teste autorizados.

    Estudantes e professores entram pelo mesmo formulário de e-mail e senha. O cadastro docente exige @unb.br no frontend e no trigger do banco; @aluno.unb.br não concede papel docente. Google cria novos perfis como student e preserva o papel de contas existentes. Atribuições administrativas continuam no painel protegido. Com confirmação de e-mail habilitada, o cadastro sem sessão mostra a orientação para confirmar antes de entrar, sem anunciar que o usuário já está autenticado.

    Verificação de 11/11/2026: o projeto agenda-unb-homolog permitia Email e cadastro, exigia confirmação e tinha Google desativado. Os testes de interface substituem o provedor externo; não comprovam entrega de e-mail nem consentimento real do Google. Esses dois fluxos devem ser homologados após a configuração remota.

    O Vite lê o ambiente na raiz do repositório (envDir: '..') e incorpora VITE_* no build. Alterar esses valores exige novo build. Não incluir senha PostgreSQL, chave de serviço ou tokens de deploy em variáveis VITE_*, exemplos ou logs. O build precisa das dependências de desenvolvimento: o SDK Supabase está declarado nessa categoria no estado atual.

    Configurar a conexão PostgreSQL usando a opção oferecida pelo projeto Supabase que seja alcançável pelo Render, preferindo pooler em modo de sessão quando necessário por conectividade. Confirmar TLS, driver psycopg e limites de conexões antes da homologação. Não afirmar que RLS protege conexões administrativas: o backend também deve aplicar suas verificações de usuário/papel.

    SPA, CORS e configuração Vercel

    Tanto frontend/vercel.json (usado quando o Root Directory é frontend) quanto vercel.json na raiz configuram exclusivamente o frontend Vite (framework: "vite", saída dist / frontend/dist), preservando /api/search (kind=sitemap e kind=event), /auth/retorno -> /app.html, /eventos -> /eventos.html e rotas profundas em /app.html.

    O roteamento do frontend gera títulos, descrições e URLs canônicas no HTML da home e da lista de eventos durante o build. As rotas da SPA, como /admin e /plano-de-ensino, continuam aceitando acesso direto e recarga.

    A função de busca responde a /sitemap.xml e /evento/<id>. Configure a URL e a chave pública do Supabase do mesmo ambiente no build e na função. As leituras passam pela RLS anônima e selecionam apenas eventos aprovados. A CDN pode guardar respostas públicas por cinco minutos. Teste o sitemap, um evento aprovado e um ID inexistente após a publicação. Após o deploy, envie o sitemap e solicite indexação no Search Console.

    A SPA consome a API no Render diretamente por HTTPS através de VITE_API_URL (exigida no build em frontend/src/lib/deploymentConfig.js, terminada em /api/v1), inclusive no upload de 10 MiB, com CORS_ORIGINS restrito às origens explícitas da Vercel no Render.

    [!WARNING] Atenção ao limite de upload (4,5 MB nas Vercel Functions): O fluxo atual de upload de planos de ensino em /api/v1/syllabus/upload suporta arquivos de até 10 MB no FastAPI. Contudo, o limite de payload de requisições nas Vercel Serverless Functions é de 4,5 MB. Arquivos maiores que esse limite serão rejeitados com HTTP 413 pela camada de borda da Vercel antes de alcançar o FastAPI. Caso uploads entre 4,5 MB e 10 MB devam ser suportados sem falhas: 1. Adotar upload direto do frontend para o Supabase Storage via client SDK com RLS ou pre-signed URLs (enviando ao FastAPI apenas metadados/referência); ou 2. Manter a execução do backend como Web Service dedicado (ex: Render/container) para as rotas com transferências volumosas.

    Fluxo de CI/CD proposto

    O workflow .github/workflows/supabase-ci.yml valida o banco em PRs e pushes na main que alteram supabase/**, backend/** ou o próprio workflow, além de permitir execução manual. Ele inicia o Supabase local com migrations e seed, reprova erros de lint e executa backend/tests/test_*database.py com Python 3.11. Os testes usam uma cópia do banco recém-inicializado (schema e seed) em agenda_catalog_ci, banco local descartável necessário para o teste de publicação que faz commits. A porta vem de supabase/config.toml; nenhuma credencial de produção é necessária. Testes pgTAP só executam quando há arquivos SQL em supabase/tests. O stack é encerrado mesmo em caso de falha. A execução no GitHub Actions ainda precisa ser confirmada.

    O restante do fluxo abaixo continua proposto; este workflow não publica a aplicação. O workflow de documentação continua independente.

    1. PR: instalar dependências; executar pytest com SQLite, testes de calendário, build frontend e MkDocs. Subir Supabase local descartável, aplicar migrações/seed e executar os testes PostgreSQL com TEST_SUPABASE_DB_URL local. Falha bloqueia promoção; teste ignorado não equivale a aprovação de RLS.
    2. Merge em main: repetir as verificações do commit final e publicar homologação, com exclusão mútua por ambiente para impedir migrações/deploys simultâneos. Somente jobs com sucesso liberam a sequência de publicação.
    3. Banco: conferir projeto de destino e migrações pendentes; aplicar migrações versionadas antes do código dependente. Usar Supabase CLI autenticada com alvo explícito e db push após revisão. Não executar db reset nem seed demonstrativo em banco persistente.
    4. Backend: publicar exatamente o SHA validado. Verificar /health e uma leitura real de eventos: /health sozinho não testa banco/Auth.
    5. Frontend: gerar build do mesmo SHA com variáveis do ambiente e publicar. Executar os testes de fumaça abaixo.
    6. Produção: acionamento manual informa o SHA homologado e exige aprovação do responsável pela release. Repetir banco → backend → frontend → fumaça com configuração de produção. Como VITE_* muda por ambiente, usar o mesmo código-fonte, não reutilizar cegamente o bundle de homologação.

    Desabilitar deploy automático independente dos provedores quando o workflow assumir a publicação; do contrário, um push pode publicar código antes das migrações ou dos testes. Preservar o SHA e o resultado de cada etapa no registro de release. Congelar versões das ferramentas/dependências em tarefa futura: as dependências Python atuais não são fixadas, portanto o mesmo SHA ainda não garante build reproduzível.

    Recuperação e acompanhamento

    • Exigir migrações compatíveis com a versão anterior durante a transição; alterações destrutivas precisam de plano próprio antes da promoção.
    • Se migração falhar, interromper a publicação. Se API/SPA falhar, restaurar a versão anterior conhecida nos provedores, conferindo compatibilidade com o schema vigente.
    • Rollback de código não desfaz migração. Para banco, priorizar migração corretiva; restauração só após avaliar perda de dados, janela e backup disponível. Verificar e ensaiar restauração em ambiente separado antes de depender dela.
    • Acompanhar logs da API, erros HTTP, falhas de autenticação e execução de migrações; registrar horário, SHA, resultado e responsável. O monitoramento completo ainda é pendência de implementação.
